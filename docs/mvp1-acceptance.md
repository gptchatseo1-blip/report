# Финальная приёмка MVP-1 после PR №14

Дата аудита: 12 августа 2026 года. База аудита: commit `ea9a267` (`main` после PR №14).

## Итог

Основная локальная цепочка MVP-1 реализована и покрыта автоматическими тестами. Перед
production-запуском обязательны HTTPS/reverse proxy, реальные секреты, проверка трёх внешних
интеграций на одном клиентском проекте и регламент резервного копирования. Внешние API нельзя
считать принятыми только по mock-тестам.

Статусы ниже означают:

- **реализовано** — код и автоматическая проверка присутствуют;
- **частично** — основной сценарий работает, но исходный критерий выполнен не буквально;
- **отсутствует** — в репозитории нет реализации или эксплуатационного механизма;
- **реальные данные** — есть адаптер и mock-тесты, но нужны учётные данные провайдера.

## Переменные окружения

### Обязательные для production

| Переменная | Назначение |
|---|---|
| `DJANGO_SECRET_KEY` | Случайный долгий ключ Django; placeholder при `DEBUG=0` блокирует старт. |
| `DJANGO_DEBUG=0` | Production-режим. |
| `DJANGO_ALLOWED_HOSTS` | Домены через запятую, без схемы. |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | Полные HTTPS origins, например `https://reports.example.ru`. |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | Отдельные реквизиты production-БД. |
| `POSTGRES_HOST=db`, `POSTGRES_PORT=5432` | Подключение PostgreSQL. |
| `DJANGO_MEDIA_ROOT=/app/media` | Каталог артефактов, смонтированный в persistent volume. |

### HTTPS за доверенным reverse proxy

После проверки HTTPS и корректного `X-Forwarded-Proto` установить:

```dotenv
DJANGO_SECURE_SSL_REDIRECT=1
DJANGO_SESSION_COOKIE_SECURE=1
DJANGO_CSRF_COOKIE_SECURE=1
DJANGO_TRUST_X_FORWARDED_PROTO=1
DJANGO_SECURE_HSTS_SECONDS=3600
DJANGO_SECURE_HSTS_INCLUDE_SUBDOMAINS=0
DJANGO_SECURE_HSTS_PRELOAD=0
```

Сначала используйте небольшой HSTS. `INCLUDE_SUBDOMAINS` и `PRELOAD` включайте только после
проверки всех поддоменов; ошибочный HSTS трудно быстро отменить.

### Интеграции и лимиты

- `MAX_UPLOAD_SIZE_MB`;
- `TOPVISOR_USER_ID`, `TOPVISOR_API_KEY`, опционально `TOPVISOR_API_BASE_URL`,
  `TOPVISOR_REQUEST_TIMEOUT_SECONDS`, `TOPVISOR_MAX_RETRIES`;
- `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`, `YANDEX_REDIRECT_URI`;
- постоянный `CREDENTIAL_ENCRYPTION_KEY` (Fernet); потеря или смена ключа делает сохранённые
  OAuth-токены нечитаемыми;
- опционально `YANDEX_OAUTH_AUTHORIZE_URL`, `YANDEX_OAUTH_TOKEN_URL`,
  `YANDEX_METRIKA_API_BASE_URL`, `YANDEX_WEBMASTER_API_BASE_URL`,
  `YANDEX_REQUEST_TIMEOUT_SECONDS`, `YANDEX_MAX_RETRIES`.

Секреты хранить в secret manager либо в `.env` с доступом только владельцу. Не передавать
`.env`, database dump или media backup в CI artifacts и не печатать их в shell с `set -x`.

## Тестовое развёртывание

1. Создать отдельный сервер/VM с Docker Compose, DNS и TLS reverse proxy.
2. Получить актуальный `main`, создать `.env` из `.env.example`, заменить все пароли и ключи.
3. Проверить конфигурацию и запустить:

   ```bash
   docker compose config --quiet
   docker compose up --build -d
   docker compose ps
   curl --fail https://reports.example.ru/health/
   docker compose exec -T web python manage.py check --deploy
   docker compose exec -T web python manage.py makemigrations --check --dry-run
   docker compose exec web python manage.py createsuperuser
   ```

4. Выполнить PostgreSQL/E2E/LibreOffice проверки в тех же контейнерах:

   ```bash
   docker compose exec -T web pytest
   docker compose exec -T web python manage.py export_smoke_demo --output /app/media/smoke
   docker compose exec -T web sh -c 'test -s /app/media/smoke/seo-demo.pdf'
   ```

5. Скачать smoke DOCX/PDF/XLSX через защищённый интерфейс или временно скопировать их
   `docker compose cp`; открыть в Microsoft Office/LibreOffice и визуально проверить кириллицу,
   графики, переносы таблиц, колонтитулы, альбомные страницы и номера страниц.

## Ручная приёмка на одном реальном проекте

Для приёмки нужны: домен проекта; варианты бренда; URL-группы и приоритеты; CSV и XLSX одного
среза; Topvisor user ID/API key и доступный проект; OAuth-приложение Яндекса с точным HTTPS
callback; аккаунт с `metrika:read` и `webmaster:read`; доступ к счётчику Метрики, его целям и
подтверждённому сайту Вебмастера. Проверяющий не передаёт токены разработчикам — он вводит
секреты в защищённое окружение и проходит OAuth сам.

1. Создать superuser, войти и убедиться, что anonymous URL перенаправляет на login.
2. В Admin создать проект, буквальное и regex-правило бренда, две пересекающиеся URL-группы с
   разными приоритетами и поисковые конфигурации.
3. Импортировать CSV: проверить preview, понятную ошибку строки, исправление, подтверждение и
   отсутствие дубля при повторе. Повторить отдельной партией XLSX.
4. Настроить `TOPVISOR_*`, открыть подключение, выбрать соответствующий проект/системы/регионы,
   синхронизировать месяц и повторить sync. Сверить несколько запросов, частотность, позиции,
   глубину, checksum и отсутствие дублей с кабинетом Topvisor.
5. Пройти OAuth Яндекса. Проверить callback, scopes, выбор правильного счётчика, цели и явное
   подтверждение несовпадающего домена. Синхронизировать и сверить визиты/пользователей/цели за
   три месяца с интерфейсом Метрики.
6. Выбрать сайт Вебмастера, синхронизировать и сверить ИКС, страницы, клики, показы и CTR за
   доступные периоды. Отсутствующие данные должны оставаться отсутствующими, не нулями.
7. Добавить категорию и несколько выполненных работ в прошлом и отчётном месяце.
8. Создать отчёт за календарный месяц и зафиксировать версию. Записать checksum snapshot.
9. Изменить исходный проект/импорт, открыть старую версию и убедиться, что её показатели и
   checksum не изменились. Для новых данных создать следующую версию.
10. Проверить narratives: отредактировать текст, сохранить, подтвердить. Запустить валидатор;
    устранить ошибки. Отдельно убедиться, что ошибка блокирует финальный экспорт.
11. Создать draft и final DOCX/PDF/XLSX, открыть файлы и выборочно сверить одни и те же
    показатели и provenance во всех форматах. Убедиться, что черновик маркирован.
12. Отключить сеть/ключи API и повторно экспортировать старую версию. Содержание должно
    сохраниться: генерация обязана идти из snapshot.
13. Проверить application/proxy logs: в них не должно быть OAuth token, client secret,
    Topvisor key, заголовков `Authorization`, содержимого `.env` или клиентского файла.

## Резервное копирование и восстановление

До ввода клиентских данных владелец обязан настроить ежедневный зашифрованный off-host backup
обоих volumes и периодическую проверку восстановления. Минимальный ручной пример:

```bash
mkdir -p backups
docker compose exec -T db pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc > backups/report.dump
docker run --rm -v report_media_data:/source:ro -v "$PWD/backups:/backup" alpine \
  tar -czf /backup/media.tgz -C /source .
```

Имена Docker volumes зависят от Compose project name (`docker volume ls`). Backup должен
включать `.env`/ключ шифрования отдельным защищённым каналом: без него OAuth-токены не
восстановятся. Тест восстановления выполнять в изолированном окружении через `pg_restore` и
распаковку media volume. Установить retention, контроль размера, шифрование, мониторинг
успешности и RPO/RTO; две локальные persistent volumes не являются резервной копией.

## Известные ограничения

- Однопользовательский режим обеспечивается процессом, а не запретом нескольких аккаунтов.
- Конфигурация проектов находится в Django Admin; ролей/Workspace нет.
- Устройство в позициях не является измерением; лимита в 3000 фраз нет.
- Внешние API зависят от тарифов, прав, sampling, доступной истории и изменений провайдеров.
- Экспорт синхронный и может занять HTTP worker; Celery/Redis намеренно отсутствуют.
- Файлы хранятся на локальном persistent volume; S3 и встроенный backup отсутствуют.
- TLS/reverse proxy, расписание backup, мониторинг и ротация секретов — ответственность
  владельца эксплуатации.
- Побитовая идентичность повторного DOCX/PDF не обещается; сравниваются snapshot, показатели и
  содержание.
