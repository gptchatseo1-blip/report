# Промт для Codex: сервис подготовки ежемесячных SEO-отчетов

Ты — senior full-stack разработчик, data engineer и архитектор внутренних аналитических сервисов. Твоя задача — спроектировать и реализовать рабочий веб-сервис для подготовки ежемесячных SEO-отчетов по нескольким клиентским проектам.

## 1. Исходный контекст

В рабочем пространстве находятся примеры реальных отчетов:

- `worldofquartz.ru_отчет_за_июнь_26.docx`;
- `quantraquartz.ru - отчет за июнь_26.docx`;
- `begma.ru_отчет_за_июнь_2026.docx`;
- `medkras.com_отчет_за_июнь_26.docx`;
- `evolutis.clinic - отчет_за_июнь_26.docx`;
- `kuncevoclinic-ok.ru_-_отчет_за_июнь_26.docx`;
- `ldck.ru_отчет_за_июнь_26.docx`.

Сначала проанализируй эти документы: структуру разделов, таблицы, изображения, формулировки выводов, различия между проектами и порядок показателей. Считай их эталонами состава данных, но не копируй из них клиентские цифры в код, тесты или демонстрационный интерфейс. Для тестов создай обезличенные синтетические фикстуры.

Общая структура отчетов:

1. Домен и отчетный период.
2. Видимость и позиции по поисковой системе и региону.
3. Распределение запросов по диапазонам топа и динамика по месяцам.
4. Таблицы запросов: фраза, частотность, позиция, группа.
5. ИКС и динамика количества страниц в поиске Яндекса.
6. Показы, клики, CTR, средняя позиция и популярные запросы из Яндекс Вебмастера.
7. Трафик из Яндекс Метрики: источники, поисковые системы, регионы, страницы входа, разделы сайта.
8. Конверсии по целям.
9. Выполненные работы, рекомендации и проектные пояснения.
10. В отдельных проектах — дополнительные регионы, рыночные ориентиры, семантика, каталоги и справочники.

## 2. Цель продукта

Нужен внутренний многопроектный веб-сервис, в котором SEO-специалист может:

1. Создать проект и указать домен, название, бренд, регионы и поисковые системы.
2. Подключить источники данных.
3. Сопоставить проект с нужным счетчиком, сайтом и проектом во внешних системах.
4. Настроить группы URL, брендовые запросы, цели и состав отчета.
5. Выбрать отчетный месяц и запустить сбор данных.
6. Увидеть источник и дату получения каждого показателя.
7. Получить рассчитанные показатели и черновики выводов.
8. Внести выполненные работы, рекомендации и ручные пояснения.
9. Проверить предупреждения контроля качества.
10. Отредактировать отчет в предпросмотре.
11. Сформировать DOCX и PDF, а таблицы запросов при необходимости выгрузить в XLSX.
12. Сохранить версию отчета и при необходимости пересобрать ее без повторного запроса данных.

Сервис должен работать и без подключения языковой модели: расчеты, диаграммы, шаблонные выводы и экспорт обязательны. Интеграция с OpenAI API может быть добавлена как опциональный режим подготовки черновика аналитического текста.

## 3. Базовый технологический стек

Если в репозитории уже есть рабочий стек, сохрани его и адаптируй архитектуру. Если проект создается с нуля, используй:

- Python 3.12+;
- Django 5.2 LTS;
- Django REST Framework для внутренних API;
- PostgreSQL;
- Redis и Celery для фоновой синхронизации и генерации документов;
- Django templates + HTMX для интерфейса внутреннего сервиса;

- `cryptography` для прикладного шифрования токенов;
- `python-docx` и/или `docxtpl` для DOCX;
- LibreOffice headless для получения PDF из финального DOCX;
- `openpyxl` для импорта и экспорта XLSX;
- Matplotlib для воспроизводимых диаграмм;
- Docker Compose для локального запуска;

Зафиксируй точные версии зависимостей. Подготовь `.env.example`, миграции, команды запуска, тестовые фикстуры и краткую документацию.

## 4. Архитектурные принципы

### 4.1. Снимок данных перед генерацией

Раздели процесс на этапы:

1. Синхронизация внешних данных.
2. Сохранение нормализованных показателей и исходных ответов API.
3. Формирование неизменяемого снимка данных отчета.
4. Расчет производных показателей.
5. Проверка качества.
6. Редактирование выводов.
7. Генерация документов из снимка.

Генератор документа должен работать со снимком, а не обращаться к внешним API во время рендера. Одна версия отчета всегда должна воспроизводиться из сохраненных данных.

### 4.2. Происхождение данных

Для каждого показателя сохраняй:

- источник;
- внешний идентификатор проекта, счетчика или сайта;
- период;
- параметры запроса;
- время получения;
- статус актуальности;
- ссылку на исходный снимок ответа;
- способ получения: API, импорт файла или ручной ввод.

В интерфейсе покажи пользователю происхождение значения и возможность открыть технические детали без отображения секретов.

### 4.3. Изоляция проектов

Каждый отчет, файл, импорт, снимок и настройка должны принадлежать конкретному рабочему пространству и проекту. Все выборки фильтруй по workspace и project. Добавь роли `admin`, `editor`, `viewer` и журнал действий.

## 5. Интеграции

Реализуй каждую внешнюю систему через отдельный адаптер с единым интерфейсом: `connect`, `test_connection`, `list_resources`, `sync`, `normalize`, `health_status`.

### 5.1. Яндекс Метрика — обязательная интеграция

Используй OAuth Яндекса и минимальный доступ `metrika:read`. Для серверного веб-приложения используй authorization code flow, `state`, безопасный callback и refresh token. После подключения получи список доступных счетчиков, чтобы пользователь выбрал счетчик в интерфейсе.

Получай агрегированные данные через Management API и Reporting API. Logs API для этого продукта не требуется.

Необходимые данные:

- список счетчиков и параметры выбранного счетчика;
- список целей;
- визиты по источникам за последние три отчетных месяца;
- поисковый трафик по поисковым системам;
- поисковый трафик по регионам;
- поисковый трафик по страницам входа;
- данные по настроенным группам URL;
- конверсии и достижения выбранных целей;
- текущий период, предыдущий равный период и помесячная динамика за квартал.

Идентификаторы метрик, измерений и фильтров вынеси в отдельный модуль. Добавь интеграционные тесты с зафиксированными обезличенными ответами API.

### 5.2. Яндекс Вебмастер — обязательная интеграция

Подключай через тот же или отдельный OAuth Яндекса с правом получать информацию о сайтах в Яндекс Вебмастере. После подключения получи ID пользователя и список доступных сайтов; пользователь выбирает нужный host.

Загружай:

- историю ИКС;
- историю количества страниц в поиске;
- статистику индексирования;
- сводные показатели поисковых запросов;
- показы, клики, CTR и среднюю позицию;
- популярные запросы и динамику относительно предыдущего равного периода.

Все используемые операции должны быть чтением данных. Сервису не нужны операции добавления сайтов, удаления сайтов, изменения Sitemap или отправки URL на переобход.

### 5.3. Topvisor — обязательная интеграция для позиций

В форме подключения пользователь вводит:

- `User-Id`;
- API key.

Передавай их серверным запросом в заголовках `User-Id` и `Authorization: bearer <API_KEY>`. После проверки соединения получи проекты, поисковые системы, регионы и устройства. Пользователь выбирает проект и нужные сочетания поисковой системы, региона и устройства.

Используй API позиций, истории, сводки и диаграммы. Получай:

- видимость;
- распределение фраз по диапазонам `1–3`, `1–10`, `11–20` или `11–30`, а также дополнительным диапазонам;
- позиции по каждой фразе;
- частотность;
- группу фразы;
- целевую страницу, если доступна;
- динамику по датам;
- поисковую систему, регион и устройство.

Видимость бери из сводных данных Topvisor. Собственный расчет видимости используй только после отдельного подтверждения формулы тестами.

Учти лимиты Topvisor: пагинацию, повтор запросов с backoff, обработку 429 и ограничение параллельности. Ключ Topvisor хранится только в зашифрованном виде.

Добавь резервный импорт CSV/XLSX. Минимальный формат строк: дата, поисковая система, регион, устройство, запрос, частотность, позиция, группа, целевой URL. Для истории сводных показателей предусмотрен отдельный лист или отдельную форму импорта.

Гостевая ссылка Topvisor может храниться как ручное поле отчета. Ее отсутствие не должно блокировать генерацию.

### 5.4. Google Search Console — опциональная интеграция

Используй OAuth 2.0 и scope `https://www.googleapis.com/auth/webmasters.readonly`. После подключения пользователь выбирает property.

GSC используется для дополнительной проверки и анализа показов, кликов, CTR, средней позиции, запросов и страниц Google. Точные региональные позиции продолжает предоставлять Topvisor. Отсутствие GSC не должно блокировать отчет, аналогичный исходным примерам.

### 5.5. Рыночные показатели Яндекс Метрики

Данные «Средние показатели по рынку» сейчас не имеют доступного публичного API. Реализуй их как опциональный ручной блок:

- загрузка изображения из интерфейса Метрики;
- ручной ввод значений и пояснения;
- отметка источника `manual_yandex_benchmark`;
- дата актуальности;
- возможность полностью скрыть раздел.

### 5.6. Выполненные работы

Это структурированные ручные данные. Добавь форму, массовое добавление и импорт CSV/XLSX со столбцами:

- дата;
- категория;
- название работы;
- статус;
- URL;
- название материала или страницы;
- объем в символах;
- ответственный;
- комментарий;
- ссылка на результат.

Поддержи шаблоны повторяющихся работ и проектные категории. В отчете показывай только выбранные пользователем записи отчетного периода.

## 6. Настройки проекта

Для проекта храни:

- название и домен;
- допустимые варианты домена и бренда;
- язык и часовой пояс;
- поисковые системы, регионы и устройства;
- идентификаторы внешних ресурсов;
- брендовые запросы: список строк и регулярных выражений;
- группы URL: название, тип, приоритет и одно или несколько правил `starts_with`, `contains`, regex;
- приоритетные направления и страницы;
- цели Метрики, включенные в отчет;
- подписи целей для клиента;
- конкурентов;
- логотип, цвета и реквизиты отчета;
- состав разделов;
- режим таблиц запросов;
- шаблон комментариев и рекомендаций.

Проверяй пересечения правил групп URL и показывай пользователю URL, попавшие сразу в несколько групп.

## 7. Расчеты

Все числа рассчитывай в коде до подготовки текста.

### 7.1. Периоды

- Текущий период — выбранный пользователем диапазон.
- Предыдущий период — непосредственно предшествующий диапазон той же продолжительности.
- Квартальная динамика — три отчетных календарных месяца, включая выбранный месяц.
- Даты рассчитывай в часовом поясе проекта.

### 7.2. Изменения

Для абсолютных показателей:

`relative_change = (current - previous) / previous * 100`.

Для процентных показателей, включая CTR, конверсию и долю запросов в топе, основной показатель изменения — процентные пункты:

`delta_pp = current - previous`.

Относительное изменение процента допускается как дополнительное значение с явной подписью. Обрабатывай нулевое предыдущее значение без деления на ноль.

### 7.3. Позиции

- Храни исходное значение позиции и нормализованный статус: число, `not_found`, `beyond_depth`, `no_data`.
- Диапазоны топа должны настраиваться для каждого отчета.
- Показывай, изменилось ли число отслеживаемых запросов. При изменении набора запросов добавляй предупреждение, что сравнение долей может быть искажено.
- Статистику по поисковым системам, регионам и устройствам рассчитывай отдельно.

### 7.4. Трафик и разделы

- Сравнивай одинаковые фильтры и одинаковую продолжительность периодов.
- Долю поисковой системы считай от всего поискового трафика выбранного периода.
- Группы страниц рассчитывай по нормализованному URL без UTM-меток, фрагментов и служебных параметров.
- Показывай долю главной страницы, самую посещаемую внутреннюю страницу и динамику каждой настроенной группы.

### 7.5. Конверсии

- Пользователь выбирает цели, которые войдут в отчет.
- Для каждой цели показывай достижения, конверсию и динамику по месяцам.
- Переименования целей во внешней системе не должны менять клиентскую подпись, сохраненную в проекте.

## 8. Генерация аналитического текста

Сделай два слоя.

### 8.1. Детерминированные шаблоны — обязательный слой

Формируй проверяемые предложения на основе рассчитанных значений:

- рост, снижение или отсутствие существенного изменения;
- абсолютное и относительное изменение;
- доля источника;
- лидер среди страниц, разделов или запросов;
- изменение ИКС и индексации;
- предупреждение о смене набора ключевых фраз;
- отсутствие данных.

Русские формы слов и знаки должны быть корректными. Разделяй «проценты» и «процентные пункты».

### 8.2. Опциональный черновик через OpenAI API

Если задан API key, языковая модель получает только агрегированный валидированный JSON, словарь проекта и список допустимых выводов. Модель готовит краткий черновик пояснений и рекомендаций.

Каждое числовое утверждение после генерации сопоставляй со снимком данных. Любое неподтвержденное число блокирует публикацию. Пользователь должен подтвердить или отредактировать текст.

Сервис полностью сохраняет работоспособность при отсутствии OpenAI API key.

## 9. Контроль качества

Перед экспортом запускай валидатор. Разделяй ошибки, блокирующие публикацию, и предупреждения.

Обязательные проверки:

1. Домен, бренд и отчетный период совпадают с настройками проекта.
2. В тексте нет доменов и брендов других проектов рабочего пространства.
3. Название поисковой системы в заголовке совпадает с источником данных.
4. Все числа в тексте существуют в снимке данных.
5. Формулы изменения пересчитаны независимо.
6. Процентные показатели сравниваются в процентных пунктах.
7. Сумма взаимоисключающих долей находится в допустимом диапазоне с учетом округления.
8. URL принадлежат проекту или явно разрешенному внешнему домену.
9. Периоды API полностью покрывают период отчета.
10. Нет дублированных абзацев и незаполненных плейсхолдеров.
11. Ссылки имеют корректный формат.
12. Для ручных данных указаны источник, автор и дата.
13. Для каждого обязательного раздела есть данные или явная отметка «данные недоступны».
14. В отчете отсутствуют токены, API keys, client secrets и технические трассировки.

Добавь регрессионные тесты на типовые ошибки, найденные в примерах:

- имя файла указывает июнь, а заголовок документа — май или другой год;
- в отчете одного проекта упоминается бренд другого проекта;
- показатель Google подписан как Яндекс;
- снижение с 33% до 31% названо снижением на 27%;
- в текст попал лишний символ или незакрытый плейсхолдер.

## 10. Интерфейс

Основные экраны:

1. Вход и выбор рабочего пространства.
2. Список проектов с состоянием подключений.
3. Мастер создания проекта.
4. Интеграции и проверка доступа.
5. Настройки URL-групп, бренда, целей и состава отчета.
6. Новый отчет: период, источники, режим, дополнительные блоки.
7. Страница синхронизации с прогрессом и журналом ошибок.
8. Предпросмотр отчета по разделам.
9. Редактор пояснений, выполненных работ и рекомендаций.
10. Контроль качества с переходом к проблемному месту.
11. История версий и скачивание DOCX, PDF, XLSX.

В предпросмотре у каждого показателя добавь действие «Показать источник». Ручные переопределения значений требуют комментария и сохраняются в журнале.

## 11. Форматы отчета

Реализуй два профиля.

### 11.1. Клиентский компактный

- основные графики и выводы;
- ограниченное число популярных запросов и страниц;
- выполненные работы и рекомендации;
- полные таблицы запросов — отдельным XLSX.

### 11.2. Полный, близкий к исходным отчетам

- разделы в порядке исходных образцов;
- подробные таблицы запросов;
- повтор заголовка таблицы на каждой странице;
- альбомная ориентация для крупных приложений;
- автоматические переносы строк;
- номера страниц и колонтитулы;
- отдельный XLSX с теми же исходными строками.

Графики строй из данных сервиса. Скриншоты интерфейсов внешних систем используй только для ручного блока рыночных показателей.

Имена файлов:

- `{domain}_отчет_{YYYY-MM}_v{version}.docx`;
- `{domain}_отчет_{YYYY-MM}_v{version}.pdf`;

## 13. Безопасность

- Все токены и API keys храни в зашифрованном виде; ключ шифрования поступает из переменной окружения или secret manager.
- В журналах показывай только маскированные идентификаторы.
- OAuth callback защищай через `state` и привязку к текущей сессии.
- Используй минимальные права чтения.
- Добавь отключение интеграции с удалением локальных токенов и понятной инструкцией по отзыву доступа у провайдера.
- Ограничь размеры и типы загружаемых файлов; проверяй XLSX/CSV перед обработкой.
- Защити фоновые задачи от повторного запуска и гонок.
- Добавь timeouts, retry с backoff, rate limiting и circuit breaker для внешних API.
- Не передавай секреты и исходные ответы API в браузер.
- Используй только агрегированные данные Метрики; пользовательские и медицинские данные посетителей сервису не требуются.

## 16. Критерии приемки MVP

MVP считается готовым, если:

1. Проект запускается одной командой через Docker Compose.
2. Можно создать проект и настроить домен, бренд, регионы, URL-группы и цели.
3. Можно импортировать позиции и вручную заполнить работы.
4. Можно подключить Яндекс Метрику, Яндекс Вебмастер и Topvisor либо использовать фикстуры в демонстрационном режиме.
5. Сервис формирует показатели для текущего, предыдущего периода и квартала.
6. Перед экспортом выполняется контроль периода, бренда, источника и арифметики.
7. Пользователь может редактировать выводы.
8. Создаются валидные DOCX, PDF и XLSX.
9. Повторная генерация одной версии дает те же цифры.
10. Все тесты проходят, а инструкция содержит команды запуска, миграций, создания администратора, тестов и резервного копирования.
