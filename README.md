# SEO Report — первый технический срез

Каркас внутреннего сервиса на Django 5.2: PostgreSQL, административный интерфейс,
проекты, брендовые правила, приоритетные URL-группы и ручной импорт позиций
Topvisor из CSV/XLSX, стабильные синтетические данные Метрики и Вебмастера, ручной
журнал выполненных работ, детерминированный расчётный слой и неизменяемые версии
отчётов. Экспорт документов намеренно не входит в этот срез.

## Запуск

```bash
cp .env.example .env
# Замените DJANGO_SECRET_KEY и пароли в .env
docker compose up --build -d
docker compose exec web python manage.py createsuperuser
```

Интерфейс администратора: <http://localhost:8000/admin/>. Проверка состояния:
<http://localhost:8000/health/> (`{"status": "ok"}`). При старте web-контейнера
миграции применяются автоматически.

Импорт позиций: <http://localhost:8000/imports/upload/>.

Синтетические источники: <http://localhost:8000/metrics/synthetic/>. Для выбранного
отчётного месяца создаются воспроизводимые обезличенные снимки Яндекс Метрики и
Яндекс Вебмастера за три календарных месяца. Повторный запуск не создаёт дубли.

Выполненные работы: <http://localhost:8000/worklog/>. Сначала создаётся категория
для проекта, затем добавляются датированные работы с ответственным, статусом,
страницей, результатом и комментарием.

## Формат импорта позиций

Перед загрузкой задаются проект, дата позиций, поисковая система, регион и обязательная
глубина проверки. Устройство
не используется. Поддерживаются CSV в UTF-8/CP1251 и XLSX размером до значения
`MAX_UPLOAD_SIZE_MB`. Количество фраз отдельно не ограничивается; записи сохраняются
в базу данных пакетами.

Обязательные столбцы:

- `Запрос`;
- `Позиция`;
- `Частотность` — целое неотрицательное число в каждой строке.

Дополнительные столбцы: `Группа`, `URL`. Также распознаются основные английские
названия столбцов. Заголовок может находиться в одной из первых 20 строк файла.

Сначала создаётся предпросмотр. Строки с ошибками сохраняются отдельно и блокируют
подтверждение. После исправления нужно загрузить новый файл. Повторная загрузка файла
с теми же проектом, датой, поисковой системой и регионом возвращает существующую
партию и не создаёт дубли.

## Принятые решения

- Домен приводится к нижнему регистру, без `www`, порта, пути и завершающей точки;
  международные домены сохраняются в IDNA. Нормализованное значение уникально.
- Брендовые строковые и regex-правила сопоставляются без учёта регистра, а
  уникальность шаблонов также регистронезависима.
- Если URL соответствует нескольким активным группам, выбирается группа с большим
  приоритетом; результат классификации содержит весь список совпадений для диагностики.
- Regex проверяются на синтаксис, длину, обратные ссылки и распространённые вложенные
  повторения, способные вызвать катастрофический backtracking.
- Управление реализовано стандартным защищённым Django Admin. Для однопользовательского
  режима создаётся один superuser командой `createsuperuser`.

## Расчётный слой

Чистые функции находятся в `apps/reports/calculations.py`, а адаптеры ORM — в
`apps/reports/services.py`. Текущая версия формул — `mvp1.2-depth-aware`; она включается в каждый
набор фактов и должна меняться при несовместимом изменении арифметики.

- Периоды — отчётный календарный месяц, предыдущий календарный месяц и окно от начала
  месяца `-2` до конца отчётного месяца. Для позиций и внешних источников формируется
  трёхмесячный ряд, пригодный для графиков и последующего snapshot.
- Для обычного показателя вычисляются абсолютная и относительная динамика; для процентов
  дополнительно вычисляется разница в процентных пунктах. При ненулевом значении и
  нулевой базе относительная динамика не определяется (`zero_base`), а при отсутствии
  одного значения все виды динамики не определяются (`missing_data`). Для `0 → 0`
  относительная динамика равна 0%.
- Потоковые счётчики Метрики, клики и показы перед сравнением нормализуются на
  календарный день; моментальные показатели индексации и ИКС, процентные и средние
  показатели сравниваются без такой нормализации. Доли источников
  считаются от визитов и проверяются на совпадение суммы. CTR пересчитывается как
  `клики / показы × 100` с допуском 0,01 п. п. Индексация, клики, показы и ИКС входят
  в общий набор динамики.
- Позиции распределяются только по подтверждённым глубиной диапазонам; непроверенные
  диапазоны отсутствуют, а не заполняются нулями. Каждый набор считается отдельно по
  паре «поисковая система + регион», без устройства. Используется последний снимок
  месяца. Частотность обязательна, число фраз не ограничено.
- Состав семантики сравнивается по нормализованным уникальным запросам. Доля изменения —
  размер симметрической разности, делённый на размер объединения; предупреждение
  создаётся при значении не менее 20%.
- Для URL выбирается совпавшая активная группа с максимальным приоритетом. В факте
  сохраняются все совпавшие группы и предупреждение `url_group_overlap` при пересечении.

## Версии и snapshot

`Report` однозначно задаётся проектом и календарным месяцем. Версия не возникает
при изменении проекта или источников: её явно создаёт сервис
`create_report_version(report=..., created_by=...)`. В одной транзакции он фиксирует
настройки проекта, календарные периоды, позиции и фактическую глубину каждой
конфигурации, видимость, синтетические источники, выполненные работы, provenance и
расчётные факты. Неподтверждённые глубиной диапазоны в расчёты не попадают, а при
изменении глубины у версии сохраняется `ranking_depth_changed`.

Payload содержит версии схемы и формул. Его SHA-256 считается по каноническому JSON
с сортировкой ключей. Зафиксированный `ReportDatasetSnapshot` нельзя изменить или
удалить через модель и Django Admin. `get_report_version_data(version)` читает только
payload snapshot и не обращается к Topvisor, импортам либо синтетическим адаптерам.
Чтобы учесть новые исходные данные или настройки, нужно явно создать следующую версию.

## Topvisor API

Read-only адаптер API v2 использует только переменные `TOPVISOR_*`. Реквизиты доступа
не сохраняются в моделях. В админке внутренний проект сопоставляется с ID проекта
Topvisor и конкретными конфигурациями поисковой системы/региона. Снимок сохраняет
исходную и нормализованную глубину, видимость, provenance, checksum и дату получения;
повторная синхронизация идемпотентна. Клиент поддерживает пагинацию, таймаут, 429 и
повторные запросы с exponential backoff и jitter и никогда не выполняет изменяющие API-вызовы.

Задайте `TOPVISOR_USER_ID` и `TOPVISOR_API_KEY` только в окружении (или в secret-хранилище
платформы), затем откройте **«Подключить Topvisor»** на странице отчётов проекта. Интерфейс
безопасно проверит доступ, предложит проект, поисковые системы и регионы. После выбора месяца
кнопка синхронизации получает позиции и обязательную частотность за трёхмесячное календарное
окно, показывает результат и открывает существующий либо новый отчёт. Статус запуска, checksum,
provenance, время получения и фактическая глубина каждой пары «система + регион» сохраняются,
а секреты — нет. Повторный запуск обновляет те же снимки без дублей.

## Детерминированные выводы и контроль качества

Для каждой зафиксированной версии сервис создаёт русскоязычные `NarrativeBlock` только из
`ReportDatasetSnapshot.payload`. Исходный `generated_text` и связанные `facts` сохраняются;
пользователь редактирует только `edited_text` и статус подтверждения, а свойство `effective_text`
выбирает редакцию при её наличии. После создания версия, раздел, тип, порядок, `generated_text`
и `facts` блока неизменяемы. Генератор не обращается к Topvisor, импортам или другим исходным таблицам и не
использует LLM.

```python
from apps.reports.narratives import generate_narratives
from apps.reports.validation import get_publication_readiness, validate_report_version

blocks = generate_narratives(version)
issues = validate_report_version(version)
readiness = get_publication_readiness(version)
```

Валидатор повторяем: при запуске он заменяет предыдущий набор автоматических проблем версии.
Ошибки блокируют публикацию и финальный экспорт; предупреждения не препятствуют черновому
экспорту. Проверка публикационной готовности всегда запускает актуальную валидацию, поэтому
непроверенная или изменённая редакция текста не может автоматически считаться готовой. Snapshot после фиксации остаётся неизменяемым.

## Интерфейс подготовки отчёта

1. Выполните миграции и создайте администратора: `python manage.py migrate` и `python manage.py createsuperuser`.
2. Запустите `python manage.py runserver` и войдите через `/admin/login/`. После входа стартовая страница — `/projects/`.
3. Проекты и источники на этом этапе настраиваются в Django Admin. На странице проекта выберите календарный месяц; сохраняется первое число месяца.
4. Нажмите «Зафиксировать новую версию». Версия содержит неизменяемый snapshot и открывается в предпросмотре.
5. В редакторе раздела можно сохранить редакцию, вернуть исходный текст или подтвердить вывод. Показатели и generated text не редактируются.
6. Панель контроля качества запускает валидатор и через HTMX обновляет проблемы и готовность к публикации.

Все рабочие страницы требуют Django-аутентификацию. Предпросмотр строится из `ReportDatasetSnapshot`, `NarrativeBlock` и `ValidationIssue`; provenance выводится без учётных данных и секретов.

### Ограничения этапа

Экспорт выполняется синхронно; настройка проектов остаётся в Django Admin.

## Экспорт зафиксированной версии

На странице версии панель **Экспорт** синхронно создаёт полный DOCX, PDF или XLSX. Перед
каждой генерацией валидатор перечитывает только неизменяемый snapshot и narratives: финальный
файл блокируется ошибками, а вариант «Черновик» разрешён и получает заметную маркировку.
Предупреждения включаются в документ и безопасный журнал. PDF всегда получается цепочкой
`snapshot → DOCX → LibreOffice headless → PDF` с отдельным временным профилем и timeout.

Готовые файлы скачиваются после входа через защищённый Django `FileResponse`; физический путь
не раскрывается. Storage использует `MEDIA_ROOT/reports/<project UUID>/<version UUID>/`.
Временный DOCX, PDF и профиль LibreOffice удаляются автоматически. XLSX содержит метаданные,
все позиции, трёхмесячную историю, Метрику/Вебмастер и выполненные работы без лимита строк.

Текущий MVP выполняет экспорт в HTTP-процессе. Большие документы могут занять значительное
время и удерживать worker; очередь Celery/Redis, фоновые повторы и прогресс относятся к
следующему инфраструктурному этапу.

DOCX полного профиля содержит отдельные графики и таблицы позиций для каждой пары поисковой
системы и региона, блоки Метрики и Вебмастера, полную таблицу запросов и provenance после
каждого раздела. Диапазоны ограничиваются фактической глубиной проверки. Значения, которых нет
в старом snapshot, обозначаются как «Данные недоступны» и не восстанавливаются из живых таблиц.
XLSX экранирует текст, начинающийся с `=`, `+`, `-` или `@`, от formula injection.

### Воспроизводимый демонстрационный проект MVP-1

Демонстрационный набор не требует OAuth, API-ключей или сети. Он идемпотентно создаёт проект
`seo-demo.invalid`, правила бренда и пересекающиеся приоритетные URL-группы, позиции Google
до TOP-20 и Яндекса до TOP-100 за три месяца, Метрику, Вебмастер и журнал работ. Повторный
запуск переиспользует отчёт, версию и неизменяемый snapshot, если содержимое не изменилось:

```bash
python manage.py create_demo_project
python manage.py create_demo_project  # проверка идемпотентности
```

Полный автоматический E2E-тест (для PDF необходим LibreOffice) запускается командой:

```bash
pytest -q tests/test_demo_e2e.py
```

Настоящий smoke-сценарий создаёт версию, запускает валидатор, дважды формирует все три формата
из одного snapshot, сравнивает их содержание, проверяет PDF и создаёт PNG каждой страницы:

```bash
python manage.py export_smoke_demo --output demo-artifacts
```

Результаты находятся в `demo-artifacts/`: `seo-demo.docx`, `seo-demo.pdf`, `seo-demo.xlsx`,
повторные `seo-demo-repeat.docx`, `seo-demo-repeat.pdf`, `seo-demo-repeat.xlsx` и превью
`seo-demo-page-*.png`. Docker CI выполняет конвертацию DOCX настоящим LibreOffice, проверяет
DOCX/XLSX, сигнатуру, число и непустое содержание страниц PDF и загружает только эти
обезличенные файлы в GitHub Actions artifact `anonymised-report-export-samples`.

## Яндекс Метрика через OAuth

Создайте OAuth-приложение в кабинете Яндекса и выдайте ему read-only разрешения
`metrika:read` и `webmaster:read`. В настройках приложения зарегистрируйте точный callback URL сервиса — он
должен полностью совпадать с `YANDEX_REDIRECT_URI` (схема, домен, порт и путь
`/yandex/oauth/callback/`). Сервис никогда не принимает callback или redirect URL от
пользователя.

Заполните переменные `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`, `YANDEX_REDIRECT_URI` и
`CREDENTIAL_ENCRYPTION_KEY` в окружении. Ключ шифрования можно сгенерировать так:

```bash
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

`CREDENTIAL_ENCRYPTION_KEY` обязан оставаться стабильным весь срок жизни подключений: после
его замены сохранённые токены расшифровать невозможно. Храните ключ, client secret и реальные
токены только в secret-хранилище платформы или локальном `.env`. **Никогда не добавляйте
реальные секреты в Git.** `.env.example` содержит только пустые значения и безопасные defaults.

После входа откройте страницу отчётов проекта и нажмите «Подключить Яндекс Метрику»:

1. авторизуйте аккаунт Яндекса;
2. выберите доступный счётчик (его название и домен повторно проверяются сервером через API);
3. при другом домене явно подтвердите выбор — это поддерживает зеркала и переезды;
4. выберите цели, сохранив их клиентские подписи;
5. укажите отчётный месяц и запустите синхронизацию.

Сервис получает отчётный и два предыдущих календарных месяца, атомарно сохраняет реальные
снимки, а затем открывает существующий или новый отчёт. Экспорт зафиксированной версии читает
только immutable `ReportDatasetSnapshot` и не обращается к API Метрики.

## Яндекс Вебмастер (read-only)

Интеграция использует то же зашифрованное `YandexConnection`, что и Метрика. OAuth запрашивает
`metrika:read webmaster:read`, а выданный набор scopes сохраняется и проверяется до обращения к
Вебмастеру. Старое подключение без `webmaster:read` необходимо повторно авторизовать в интерфейсе.

Настройте `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`, `YANDEX_REDIRECT_URI` и
`CREDENTIAL_ENCRYPTION_KEY`; при необходимости переопределите
`YANDEX_WEBMASTER_API_BASE_URL` (по умолчанию `https://api.webmaster.yandex.net/v4`),
`YANDEX_REQUEST_TIMEOUT_SECONDS` и `YANDEX_MAX_RETRIES`. Redirect URI должен совпадать с URI
приложения в OAuth Яндекса.

На странице подключения проекта пользователь выбирает только сайт из ответа API. Для другого
домена требуется отдельное подтверждение. Синхронизация получает пользователя, доступные сайты,
карточку и summary сайта, ИКС, страницы в поиске, события добавления/исключения и общую историю
запросов с `device_type_indicator=ALL`. Загружаются отчётный и два предшествующих календарных
месяца. Все ответы проверяются до одной атомарной записи; повторный запуск заменяет те же снимки.
Отсутствующие показатели не превращаются в нули. Снимки содержат checksum, фактический период,
время получения и безопасный provenance, но не OAuth-токены и не сырые секреты.

Интеграция не содержит операций добавления, удаления, подтверждения сайтов или переобхода.
Зафиксированная версия отчёта, preview, DOCX и XLSX работают с `ReportDatasetSnapshot`, поэтому
последующие обращения к live API для экспорта не нужны. Старые версии без данных Вебмастера
остаются совместимыми и показывают «Данные недоступны».
